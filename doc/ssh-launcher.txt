1. INTRODUCTION                                              *ssh-launcher-intro*

ssh-launcher.nvim keeps your SSH fleet inside Neovim: a searchable list of
hosts, a form that understands anything you paste into it, a rules engine that
explains why a connection will fail before you try it, and sessions that open
in a tab, a split, a float or a tmux window.

Design commitments:

- The ssh command line is built as an argument list and handed straight to the
  process. No shell is involved, so no hostname, key path or remote command can
  ever be interpreted as a shell command.
- Host-key verification is never silently disabled. `StrictHostKeyChecking=no`
  is rejected in configuration and reported as an error on any host that sets
  it.
- Outside the explicit configured-workspace action, key material is never read,
  stored, copied or logged. The plugin stores paths and metadata; passphrases
  live in your agent, where they belong. Workspace launches clearly confirm
  before copying the selected Neovim configuration directory to a host.
- Everything the interface shows is real buffer text. Colour and glyphs are
  decoration on top of information that is already readable without them.

2. REQUIREMENTS                                       *ssh-launcher-requirements*

Required~
  - Neovim 0.10 or newer
  - `ssh` (OpenSSH client) on $PATH

Optional~
  - `ssh-add`      loading passphrase-protected keys into the agent
  - `ssh-keygen`   fingerprints, key inspection, known_hosts repair
  - `ssh-copy-id`  installing your public key on a remote host
  - A Nerd Font    prettier glyphs; ASCII is used automatically without one
  - telescope.nvim, fzf-lua or snacks.nvim as an alternative picker
  - Configured workspaces: local `tar` and `scp`; remote `nvim` and `tar`

Run `:checkhealth ssh_launcher` to see what is present on your machine.

4. QUICK START                                          *ssh-launcher-quickstart*

  1. Copy an ssh command from your cloud console, a runbook or a colleague's
     message.
  2. `:Ssh` to open the manager, then press `p`.
     The clipboard is parsed and the form opens pre-filled.
  3. `<C-s>` to save, `<CR>` in the manager to connect.

Already have hosts in `~/.ssh/config`? They appear in the list automatically,
marked read-only. Press `i` to copy them into the plugin's own store so you can
edit them.

5. COMMANDS                                                *ssh-launcher-commands*

                                                                         *:Ssh*
:Ssh                    Open the host manager.
:Ssh {name}             Connect to the saved host {name} (a unique prefix is
                        enough). If nothing matches, {name} is parsed as a
                        connection string, so `:Ssh deploy@10.0.0.4` and
                        `:Ssh ssh -p 2222 root@box` both work.

:Ssh open               Open the manager.
:Ssh connect [{name}]   Connect; with no argument, pick a host.
:Ssh add [{text}]       Open the editor for a new host, seeded from {text}.
:Ssh edit [{name}]      Edit a saved host.
:Ssh delete {name}      Delete a saved host (asks first).
:Ssh list               List saved hosts.
:Ssh diagnose [{name}]  Report every problem found, for one host or all.
:Ssh import [{file}]    Import from `~/.ssh/config`, or from a JSON file.
:Ssh export [{file}]    Write saved hosts into the managed block of
                        `~/.ssh/config`.
:Ssh agent              Inspect and manage ssh-agent identities.
:Ssh sessions           Jump to a running session.
:Ssh browse [{name} [{path}]]
                        Browse and edit a host's files over SSH. {path} defaults
                        to the host's Remote dir, then its home directory.
:Ssh transfer [{name} [{path}]]
                        Two panes, this machine and a host: select files in
                        either and copy them across. See
                        |ssh-launcher-commander|.
:Ssh upload [{name} {local}... [{remote}]]
                        Send files or directories to a host. See
                        |ssh-launcher-transfer|.
:Ssh download [{name} {remote} [{local}]]
                        Fetch a file or directory from a host into the current
                        directory, or into {local}. See |ssh-launcher-transfer|.
:Ssh workspace [{name} [{path}]]
                        Copy this Neovim configuration into an isolated remote
                        session and launch Neovim on the server.
:Ssh tunnels [{name}]   List open tunnels; with a name, raise or drop that
                        host's port forwards as background processes.
:Ssh fleet {command}    Run {command} on every host. `--tag=prod` narrows it.
:Ssh history [{name}]   Show the connection log.
:Ssh keygen             Generate a new key pair.
:Ssh reload             Re-read the host database and `~/.ssh/config`.
:Ssh health             Run `:checkhealth ssh_launcher`.
:Ssh doctor             Diagnose session windows that open and then vanish:
                        lists open sessions, whether each is on screen, and the
                        autocommand groups that could be interfering.
:Ssh version            Print the plugin version.

Completion works for subcommands, host names and file paths.

Legacy names~
The 1.x commands still work: `:SshLauncher`, `:SshAddKey`, `:SshEditKey`, plus
`:SshConnect`, `:SshAgent`, `:SshSessions` and `:SshDiagnose`. Set
`commands.legacy = false` to omit them.

6. THE MANAGER                                              *ssh-launcher-manager*

The manager lists every host with its health, target, key and last use. The
detail pane underneath shows the exact command that will run and any problems
found.

Default mappings (all configurable, see |ssh-launcher-config|):

  <CR> o        connect
  <C-x>         connect in a horizontal split
  <C-v>         connect in a vertical split
  <C-t>         connect in a new tab
  S             jump to a running session
  y             copy the resolved ssh command

  a             add a host
  p             add from the clipboard
  e             edit
  c             duplicate
  r             rename
  d <Del>       delete (the marked hosts, or the one under the cursor)
  <Space>       mark / unmark
  M             clear marks

  L             raise or drop this host's port forwards
  !             run one command on every marked host
  b             browse the host's files
  n             launch remote Neovim with this configuration
  T             two panes: browse this machine and the host, copy across
  U / W         upload / download a file
  K             forget this host's key in known_hosts

  D             show every problem; 1-9 there applies a single fix
  f             apply every safe fix
  P             re-check reachability
  A             ssh-agent menu
  C             ssh-copy-id to this host
  G             generate a key pair

  /             filter as you type
  <Esc>         clear the filter, or close
  s             change the sort order
  R             reload from disk
  i             import
  X             export
  ?             help
  q             close

Marks make bulk work practical: mark ten hosts with `<Space>`, then `f` to
repair them all or `X` to export just those.

Remote workspace                                      *ssh-launcher-remote-files*
Press `b` on a host, or use `:Ssh browse {name} {path}`. The built-in browser
uses that saved host's port, identity, ProxyJump, host-key policy and ssh
options; it does not depend on those details also existing in ssh_config.

  <CR> l e      open a directory or text file
  h -           parent directory
  r R           refresh
  <C-x>         open in a horizontal split
  <C-v>         open in a vertical split
  <C-t>         open in a new tab
  q             close the browser

An opened file is a normal listed Neovim buffer: motions, undo, completion and
filetype detection work as usual. `:write` writes the current contents
back to the server. Existing files are replaced through a same-directory
temporary file so an interrupted connection does not leave a truncated file;
permissions are preserved. Binary files are refused by the text editor and can
still be moved explicitly with `U` / `W` or |:Ssh-upload| / |:Ssh-download|
(see |ssh-launcher-transfer|).

Remote operations are non-interactive so a background job can never hide a
password prompt. If a configured private key is locked, the browser offers to
load it into ssh-agent first. Oil and netrw users can opt back into their URL
adapters with `remote.adapter`.

Transferring files                                    *ssh-launcher-transfer*
                                           *:Ssh-upload* *:Ssh-download*
Copy files between this machine and a saved host with scp. The transfer uses
the host's port, identity, ProxyJump and host-key policy, runs in a small
terminal so passphrase prompts and progress are visible, and closes itself when
it succeeds. A failed transfer leaves its window open with scp's own message.
>vim
    :Ssh upload {host} {local}... [{remote}]
    :Ssh download {host} {remote} [{local}]
<
With no arguments, or with only a host, you are asked for the paths; the file in
the current buffer is offered first. `:Ssh upload` and `:Ssh download` with no
host pick one.

Uploads~
  {local}   One or more files or directories. `~`, `$VAR`, globs (`*.log`) and
            `%` (the current file) work. A directory is sent recursively. Names
            with spaces need a backslash: `my\ file.txt`.
  {remote}  Where they go. With several {local} paths the last argument is
            always {remote}, as with scp. Omitted, files land in the host's
            Remote dir, or its login directory.

Downloads~
  {remote}  A file, directory or glob on the host. Directories come down
            recursively. Escape spaces as above.
  {local}   A directory to place it in, or a new name. Omitted, the current
            directory.

Examples: >vim
    :Ssh upload web-01 %
    :Ssh upload web-01 dist/ /srv/app/
    :Ssh upload web-01 *.conf nginx.d /etc/nginx/
    :Ssh download web-01 /var/log/app.log
    :Ssh download web-01 /var/log/app.log ~/logs/app-today.log
<
Safeguards~
  - Local paths are checked before scp starts: a typo, a pattern that matches
    nothing, or a destination directory that does not exist is an error
    message, not a half-finished transfer.
  - Uploading to a host tagged as production (|ssh-launcher-config|
    `security.production_tags`) asks first.
  - A download never replaces an existing local file without asking.
  - Unsaved edits are not part of an upload: if a buffer being sent has
    changes, a warning says the saved version was sent.
  - Add `!` (`:Ssh! upload …`) to skip the production and overwrite prompts.

Tab completion offers saved hosts, then local paths. Remote paths are not
completed. In the manager `U` and `W` run the same prompts for the host under
the cursor. If the key needs a passphrase, ssh asks for it in the transfer
window.

To browse instead of typing paths, use the two-pane window
(|ssh-launcher-commander|).

Two-pane transfer                                    *ssh-launcher-commander*
                                                          *:Ssh-transfer*
>vim
    :Ssh transfer [{host} [{remote path}]]
<
Press `T` on a host in the manager, or run the command. This machine is on the
left and the host on the right, each with names, sizes and modification times.
Move around either one like any Neovim buffer (`/` searches, `gg` and `G` work),
select what you want, and copy it to the other side.

  `c` copies the selection - or the file under the cursor - into the directory
  the OTHER pane is showing. From the left pane that is an upload; from the
  right pane it is a download. There is no path to type.

Keys (all configurable under `commander.keymaps`; `?` lists the live ones):

  <CR> l        open a directory, or edit the file under the cursor
  h - <BS>      parent directory (the cursor lands on where you came from)
  <Tab>         switch between the panes
  <Space>       select or unselect the entry, then move down
  *             select everything shown; again to unselect it
  u             clear the selection        <Esc>  clear it, or else close
  c             copy to the other pane
  m             make a directory (parents included) in this pane
  go            go to a typed path; a relative path is taken from here
  .             show or hide dotfiles in this pane
  r             reload this pane
  x             cancel the running transfer and anything queued behind it
  ?             list the keys          q  close

A selected entry shows `[x]` and the pane footer counts them with their total
size. The active pane's title starts with an arrow.

Transfers run in the background and report in the status line under the panes,
with elapsed time and anything queued; both directories stay usable meanwhile
and the destination pane refreshes when a copy finishes. Because a background
transfer cannot ask for a passphrase, a locked key is offered to ssh-agent when
the window opens, exactly as for |ssh-launcher-remote-files|; hosts that need a
typed password should use `:Ssh upload` / `:Ssh download`, which run scp in a
terminal.

Safeguards~
  - Files that already exist at the destination are listed and need a yes
    (`commander.confirm_overwrite`). A "no" leaves your selection as it was.
  - Uploading to a production-tagged host asks first, as `:Ssh upload` does.
  - Names are sent literally: a file called `report[1].txt` is that file, not
    a pattern.
  - Closing the window while a copy runs lets it finish; the result is still
    reported.

Configured remote Neovim                         *ssh-launcher-remote-neovim*
Press `n` on a host, or run `:Ssh workspace {name} {path}`. The plugin packages
the configuration directory used by the current Neovim, transfers it with scp,
and starts `nvim .` on the server in the requested directory. This is a real
remote Neovim process: its plugins, LSP servers, Git commands, searches,
terminals and shell commands all execute on the server.

The copied configuration lives in a private, per-session directory and is
deleted when remote Neovim exits or the SSH connection closes. Plugin data,
state and caches persist below `workspace.remote_root`, isolated from the
server account's normal Neovim installation, so later launches do not need to
install every plugin again. The user's normal remote `~/.config/nvim` is never
read or overwritten.

The first launch to each host during a local Neovim session asks before copying
the config. Review local config for embedded tokens or credentials before
sending it to a server; environment-managed secrets are not copied. On a
production-tagged host, confirmation is required every time.

7. THE EDITOR                                                *ssh-launcher-editor*

The editor is an ordinary buffer of `Label: value` lines. Every Vim motion,
register and undo works, and a screen reader reads it as text rather than as
widget state.

  <Tab> <S-Tab>   move between fields
  <CR>            start editing the field under the cursor
  <C-g>           pull a connection out of the clipboard
  <C-k>           choose from the private keys found in `~/.ssh`
  <C-d>           explain the problem on this line
  ]d [d           next / previous problem (standard |vim.diagnostic| mappings)
  <C-f>           apply every safe fix
  gx              show the exact ssh command that will run
  <C-s> :w        save
  <C-a>           save and connect
  q               close (asks about unsaved changes)
  <C-c>           close, discarding changes

Fields~
  Name          label shown in the picker and exported to ssh_config
  Host          hostname or IP; no user, no port
  User          remote user; empty means "whatever ssh_config says"
  Port          empty means 22
  Key           private key path; empty means the agent decides
  Jump          bastion to hop through (`ProxyJump`)
  Tags          comma separated; used for filtering and policy
  Forwards      `L 8080:localhost:80, R 9000:localhost:9000, D 1080`
  Remote dir    cd here after connecting
  Command       run this instead of a login shell
  Options       extra `ssh -o` pairs, `Key=Value` separated by commas
  Notes         free text. Never store secrets here.

Every field is single-line, including Command and Notes. `ssh_config` cannot
express a newline in any directive, so a multi-line value could never be
exported or edited; one arriving from an import or a hand-edited database has
its line breaks replaced with spaces, and the editor says so when it opens.
Use `;` or `&&` to chain remote commands.

Problems are published through |vim.diagnostic| against the buffer, so they
appear in whatever diagnostic UI you already use.

8. PASTING CONNECTIONS                                        *ssh-launcher-paste*

The first line of the editor is a Paste field. Drop anything connection-shaped
into it and the fields fill in; the Paste line then clears itself.

Understood formats: >
    ssh -i ~/.ssh/k.pem -p 2222 ec2-user@10.0.0.4
    ssh -o ProxyJump=bastion deploy@app-01 'journalctl -fu api'
    ssh://deploy@app-01.internal:2222/srv/app
    deploy@app-01:2222
    root@[2001:db8::1]:2222
    scp -i key.pem file.tar deploy@app-01:/tmp/
    rsync -e "ssh -p 2222" ./dist deploy@app-01:/srv
    Host prod
      HostName 10.0.0.4
      User deploy
    { "host": "10.0.0.4", "user": "deploy" }
    Host: 10.0.0.4   User: deploy   Port: 2222
    10.0.0.4
<
Shell prompt characters (`$`, `#`, `>`), `sudo`, quoting, backslash line
continuations and trailing remote commands are all handled.

Two things are deliberately NOT carried over:

- `StrictHostKeyChecking=no` — you are told it was dropped and why.
- Anything that looks like a password or a private key — the paste is refused
  with an explanation of where that material should live instead.

`p` in the manager reads the clipboard directly, so the common case is one
keystroke.

9. DIAGNOSTICS                                          *ssh-launcher-diagnostics*

Every host is continuously checked against roughly forty rules covering the
address, the user, the port, the key file, the jump host, port forwards, ssh
options, duplicates, known_hosts and security policy.

Each finding carries a severity, an explanation of why it matters and, where
one exists, a fix.

Fixes come in two kinds:

  automatic   safe and unambiguous: `chmod 600` a key, strip a URL scheme out
              of the Host field, split `user@host`, switch a host away from
              `StrictHostKeyChecking=no`, bind a wildcard forward to
              localhost, correct a misspelled ssh option. `f` in the manager
              and `<C-f>` in the editor apply all of these.

  confirmed   anything that guesses at your intent or starts an interactive
              process: choosing which key identifies you, or running `ssh-add`.
              These are never applied unattended. Press `D` for the list and a
              number key to run one.

Before a connection opens, blocking problems stop it with a dialog offering to
fix them, edit the host, or connect anyway. Set
`diagnostics.on_connect = "warn"` to make that advisory, or `"off"` to skip it.

Network checks (DNS resolution and a TCP probe) run in the background on
libuv and never block the editor.

                                                             *ssh-launcher-unlock*
Unlocking keys~
A passphrase-protected key that is not loaded in the agent makes ssh either
prompt inside the session or fail outright, once per connection. When one is
about to be used, connecting stops and offers to load it:

    Unlock it now                     runs ssh-add; the passphrase is asked
                                      for once, and every later connection
                                      with that key is unattended
    Connect without it                dial anyway and let ssh do the asking
    Never ask again for this session
    Cancel

If no agent is running at all, one is started for this Neovim session and
stopped again when you quit — a stray agent holding unlocked keys after the
editor closes would be worse than not offering this.

The same offer appears if a connection fails with status 255 and the host's key
turns out to be the likely reason; accepting it unlocks and redials.

Unencrypted keys never trigger any of this: they work straight off disk, so
prompting about them would be noise. Control the whole behaviour with
`ssh.auto_add_keys` ("prompt", "always", "never").

10. DIAGNOSTIC CODES                                          *ssh-launcher-codes*

Silence a code with `diagnostics.disabled = { "SSH090" }`, or change its
severity with `diagnostics.severity_overrides = { SSH012 = "off" }`.

Address and identity~
  SSH001  host is empty
  SSH002  host contains whitespace
  SSH003  host still contains a `user@` part
  SSH004  host contains a URL scheme
  SSH006  host is not a valid hostname or IP
  SSH007  host is a short name that needs a search domain or alias
  SSH010  no user set
  SSH011  user contains an invalid character
  SSH012  connecting as root
  SSH020  port is not a whole number in 1-65535
  SSH080  name is empty
  SSH081  another saved host has the same name
  SSH082  another saved host points at the same target
  SSH083  the name collides with an ssh_config Host alias

Keys~
  SSH030  key file does not exist
  SSH031  key path is a directory
  SSH032  key is the public half
  SSH033  key permissions are too open        (ssh will refuse it)
  SSH034  `~/.ssh` permissions are too open
  SSH035  key is a PuTTY `.ppk` file
  SSH036  key is passphrase-protected and not loaded in the agent
  SSH037  key cannot be read
  SSH038  file does not look like a private key
  SSH039  file is an X.509 certificate
  SSH040  key sits in a git working tree or a world-readable directory
  SSH041  no key set and the agent holds no identities
  SSH042  key algorithm is deprecated or too small

Routing~
  SSH050  the jump host is this host
  SSH051  the jump host resolves through ssh_config rather than here
  SSH052  malformed jump specification
  SSH060  invalid port-forward specification
  SSH061  forward binds every interface

Options and policy~
  SSH070  ssh does not know that option
  SSH071  host-key checking is disabled for this host
  SSH072  agent forwarding is enabled
  SSH073  an option value looks like a secret
  SSH090  no known_hosts entry yet
  SSH100  a field looks like it contains a credential
  SSH120  host is tagged as production

Network (asynchronous)~
  SSH110  the name does not resolve
  SSH111  nothing is listening, or the host did not answer

11. SECURITY MODEL                                         *ssh-launcher-security*

No shell, ever~
Commands are built as argument lists and executed directly. A host named
`example.com; rm -rf /` cannot run anything — and is rejected as an invalid
hostname besides.

Host keys are verified~
The default policy is `accept-new`: the first key is trusted and recorded, and
any later change is reported. `no` is refused unless you set both
`ssh.strict_host_key_checking = "no"` and `diagnostics.allow_insecure = true`,
and even then every affected host is flagged.

No secrets on disk~
The host database holds paths and metadata. Pasted passwords are discarded,
pasted private keys are refused, and fields that look like credentials are
reported as errors. The database is written atomically with mode 0600, and
loose permissions on it are tightened on sight.

Agent forwarding is opt-in~
`-A` lets anyone with root on the far end use your loaded keys. It is off by
default, warned about when enabled, and `ProxyJump` is suggested instead.

Keys are offered narrowly~
When a host names a key, `IdentitiesOnly=yes` is added so a large agent cannot
exhaust the server's `MaxAuthTries` before the right key is tried.

Production is a speed bump~
Hosts tagged `prod`, `production` or `live` (configurable) ask for confirmation
before a session opens.

Concurrent editors do not clobber each other~
Before every write the on-disk timestamp is compared with what was loaded; if
another Neovim wrote in the meantime, the two sets are merged per host by
modification time rather than overwritten.

12. ACCESSIBILITY                                     *ssh-launcher-accessibility*

Accessibility here is a property of the data model, not a mode you switch on.

Never colour alone~
Every status has a glyph AND a word. Rows carry a text marker (`up`, `dn`,
`err`) alongside the icon; severities are spelled out in full in dialogs and
diagnostic views.

Everything is text~
Windows are ordinary buffers. There is no information that exists only as a
highlight, a virtual-text overlay or a border decoration.

Screen readers~
`a11y.announce` echoes state changes to the message area, the one surface every
screen reader observes: what opened, what was filled in from a paste, how many
hosts matched a filter, and the full state of the row under the cursor as you
move.

Keyboard only~
No action anywhere needs a mouse. Dialogs accept cursor movement plus `<CR>`,
a number, or a mnemonic letter.

Colourschemes and contrast~
Highlights link to standard groups (`DiagnosticError`, `Title`, `Comment`, …)
with `default = true`, so your theme wins and your own overrides win over that.
`a11y.high_contrast` adds weight and underline instead of relying on hue.

Without a Nerd Font~
`ui.icons` defaults to `"auto"` and follows `vim.g.have_nerd_font`. ASCII
glyphs are used otherwise; `a11y.ascii = true` forces them.

Relevant options: `a11y.ascii`, `a11y.announce`, `a11y.text_markers`,
`a11y.high_contrast`, `a11y.reduce_motion`, `a11y.virtual_text`,
`a11y.diagnostics_panel`.

13. SSH_CONFIG INTEGRATION                              *ssh-launcher-ssh-config*

Reading~
`~/.ssh/config` is parsed on startup, including `Include` directives. Hosts
appear in the manager marked read-only; wildcard patterns and `Match` blocks
are skipped because they cannot be represented as a single host. Editing one
and saving forks an editable copy into the plugin's own store.

Writing~
`:Ssh export` writes your saved hosts into a delimited block: >
    # >>> ssh-launcher.nvim managed block >>>
    Host prod-api
      HostName 10.0.4.12
      User deploy
      IdentityFile ~/.ssh/prod
      IdentitiesOnly yes
    # <<< ssh-launcher.nvim managed block <<<
<
Only that block is ever rewritten; everything you wrote by hand is preserved,
and a `.ssh-launcher.bak` copy is made first. After exporting, plain
`ssh prod-api` works outside Neovim too.

Preview the result before writing with `X` in the manager.

14. CONFIGURATION                                             *ssh-launcher-config*

Defaults in full: >lua

Connection multiplexing                                *ssh-launcher-multiplex*
`ssh.control_master = true` reuses one authenticated channel for every
subsequent connection to the same host. Reconnects become near-instant, which
matters when you open a dozen shells on the same machine.

Project-local hosts                                      *ssh-launcher-project*
A `.ssh-launcher.json` file in the working directory is loaded as a read-only
source, so a repository can ship its own staging hosts. Use the same format as
`:Ssh export` produces.

15. LUA API                                                      *ssh-launcher-api*

>lua
    local ssh = require("ssh_launcher")

    ssh.setup(opts)             -- optional
    ssh.open(opts)              -- open the manager
    ssh.pick(opts)              -- pick with the configured picker, then connect
    ssh.connect(target, opts)   -- name, host table, or any parseable string
    ssh.add(text)               -- open the editor, seeded from text
    ssh.edit(name)
    ssh.delete(name)
    ssh.diagnose(name)          -- nil for a report on every host
    ssh.import({ from = path }) -- omit `from` for ~/.ssh/config
    ssh.export({ path = path, dry_run = false })
    ssh.agent()
    ssh.sessions()
    ssh.browse(name, path)     -- pick a host when name is nil
    ssh.transfer(name, path)   -- two-pane window; pick a host when name is nil
    ssh.upload(name, paths, remote, opts)    -- paths is a list; opts.force skips prompts
    ssh.download(name, remote, dest, opts)   -- opts.on_done(ok, msg) reports the result
    ssh.workspace(name, path)  -- configured Neovim running on the host
    ssh.hosts()                 -- the host list, for scripting
    ssh.save(spec)              -- add a host from a table or a string
    ssh.health()
<
Example — connect to whatever is under the cursor: >lua
    vim.keymap.set("n", "<leader>sc", function()
      require("ssh_launcher").connect(vim.fn.expand("<cWORD>"))
    end, { desc = "SSH to the word under the cursor" })
<
Example — seed a repository's hosts at startup: >lua
    for _, spec in ipairs({ "deploy@web-01", "deploy@web-02" }) do
      require("ssh_launcher").save(spec)
    end
<
Lower-level modules (`ssh_launcher.parser`, `.diagnostics`, `.store`,
`.host`, `.keys`, `.agent`, `.probe`, `.sshconfig`) are documented in their
source headers and are safe to use directly.

17. TROUBLESHOOTING                                 *ssh-launcher-troubleshooting*

Start with `:checkhealth ssh_launcher`. It checks the OpenSSH tooling,
permissions on `~/.ssh` and on every discovered key, the agent, your
`ssh_config`, and every saved host.

"It asks for my passphrase every time"~
It should not: when a host's key is passphrase-protected and missing from the
agent, connecting offers to `ssh-add` it first — see |ssh-launcher-unlock|. If
you dismissed that prompt, press `A` in the manager to load the key by hand.
On macOS it is added with `--apple-use-keychain`, so it is asked for once ever.

                                                             *ssh-launcher-marker*
Recognising a session buffer~
Window guards, layout invariants, tab hooks and terminal managers all need a
way to tell "my terminal" from "someone else's". Session buffers are marked
before they are ever displayed, so the very first event a guard sees can
already identify them:
>lua
    vim.b[buf].ssh_launcher == true                          -- the marker
    require("ssh_launcher.terminal").is_session_buffer(buf)  -- the same test
<
The buffer is also named `ssh-launcher://<host>/<job>`. Prefer the marker: it
is set earlier and is not affected by renames.

A layout guard should bail out on a tab that contains one: >lua
    local function foreign_terminal(tab)
      for _, win in ipairs(vim.api.nvim_tabpage_list_wins(tab)) do
        local buf = vim.api.nvim_win_get_buf(win)
        if vim.bo[buf].buftype == "terminal" and not is_mine(buf) then
          return true
        end
      end
      return false
    end
<
Reshaping windows around a connecting session is what tears it down: closing
or deleting the buffer closes the pty, and that kills ssh. When it happens
anyway, it is detected and the session is reconnected — see
|ssh-launcher-window| — but not being interfered with is faster and quieter.

                                                           *ssh-launcher-terminal*
Working with another terminal plugin~
Floating-terminal managers (floaterm, toggleterm and friends) hook `TermOpen`
for every terminal buffer, including this plugin's. That can move or close a
session window straight after it opens.

Worse, some of them destroy the buffer in order to re-host it. Destroying the
buffer closes the pty, which kills ssh — the connection dies before it is made,
and `:Ssh sessions` shows nothing.

A related idiom deletes terminal buffers when the process exits: >lua
    vim.api.nvim_create_autocmd("TermClose", { command = "bdelete!" })
<
That does not break the connection, but it does throw away the transcript,
which is where ssh explains itself. The last output of a failed session is
copied out before any such handler can run, and included in the message, so a
failure always says why. The window layout events are protected the same way.

Nothing needs configuring for this. `terminal.protect = "auto"` (the default)
looks for third-party `TermOpen` hooks before opening a session and keeps them
away from it, so the very first connection works. If one gets through anyway,
the session is reconnected automatically and every later one is protected.

To go further, hand window creation to the plugin you already use:
>lua
    require("ssh_launcher").setup({
      terminal = {
        -- Any function that puts the given buffer on screen.
        strategy = function(buf, opts)
          require("toggleterm.terminal").Terminal
            :new({ bufnr = buf, direction = "float", display_name = opts.title })
            :open()
        end,
      },
    })
<
The function receives this plugin's terminal buffer and only has to display
it. If it raises, or returns without showing anything, the session falls back
to a tab rather than being lost.

                                                             *ssh-launcher-window*
"connecting to …" but no terminal appears~
The session started — the process is running — but something took its window
away. This is always outside the plugin: an autocommand on `TermOpen` or
`WinEnter`, a session or layout manager, or a picker restoring the layout it
captured when it opened.

Three defences cover this, in order:

  1. Handlers on the events fired while a session opens are suppressed when
     any third-party handler is installed (`terminal.protect`, default "auto").
  2. If the window is closed anyway, it is reopened (`terminal.ensure_visible`).
  3. If the *buffer* is destroyed — which kills ssh with it — the session is
     reconnected, once, with events suppressed. This is detected however it
     happens, including from a timer or a debounce that no event shielding
     could have prevented, for the first five seconds of a session's life.
     After that, a buffer going away is taken to be your own doing.

To find the cause: >
    :Ssh doctor
<
which lists the open sessions, whether each is on screen, and every
autocommand group hooked to the events that could interfere. Then either fix
that group, or stop it running at all: >lua
    require("ssh_launcher").setup({
      terminal = { eventignore = { "TermOpen" } },  -- or { "all" }
    })
<
`terminal.noautocmd = true` is a lighter version that only covers the window
command; it does NOT stop a `TermOpen` hook, because that event comes from
the job rather than the window.

Meanwhile `:Ssh sessions` always lists what is running and jumps to it, so a
session is never actually lost.

What a session's exit means~
The same status means different things depending on whether a session ever
existed, so it is reported accordingly:

  before a session exists    255 is ssh failing to connect. The last lines it
                             printed are included, because that is the reason.
  after one has been running 255 means the connection was closed. Any other
                             non-zero status is the remote shell's — usually
                             the last command you ran — and is mentioned, not
                             warned about.
  exit 0                     nothing is reported.

A session counts as established after five seconds (`terminal.ESTABLISHED_MS`).

"the connection was hung up" / "exited with status 129"~
129 is `128 + SIGHUP`. A local `ssh` receives that when its pty is destroyed,
which only happens when the terminal buffer goes away — closing the window,
`:bdelete`, `'nohidden'` unloading it, or quitting Neovim. It is therefore
always a local teardown, never a remote problem, and is no longer reported at
all. Remote failures arrive as status 255 with an explanation instead.

"WARNING: UNPROTECTED PRIVATE KEY FILE"~
Code SSH033. Press `f`; the key is chmod'ed to 0600 and `~/.ssh` to 0700.

"Too many authentication failures"~
The agent offered every key it holds before reaching the right one. Set the Key
field on the host — `IdentitiesOnly=yes` is then added automatically.

"Permission denied (publickey)"~
Press `D` on the host. Common causes: the public key is not in the remote
`authorized_keys` (press `C` to install it), the wrong user, or a key the
server does not accept (SSH042).

The connection just hangs~
Check the detail pane for the network line. A timeout usually means a firewall
or a missing VPN; `refused` means sshd is not listening on that port.

Seeing a session that will not close~
`S` lists live sessions. In a dead one, `q` closes the window.

Debug logging~
Set `log_level = vim.log.levels.DEBUG`; a log is written to
`stdpath("log")/ssh-launcher.log`, including the exact argv of every
connection.

18. MIGRATING FROM 1.x                                    *ssh-launcher-migration*

Nothing is required. The old `hosts.json` (a bare array of
`{name, user, host, key}`) is detected on first load, backed up under
`ssh_launcher/backups/`, and rewritten in the current schema. The `key` field
becomes `identity_file` and keeps working if you hand-edit it back.

`:SshLauncher`, `:SshAddKey` and `:SshEditKey` all still exist.

Two behaviours deliberately changed:

- 1.x passed `-o StrictHostKeyChecking=no` on every connection, which accepts
  any host key without verification. The default is now `accept-new`.
- 1.x built the command by string concatenation. Commands are now argument
  lists, so a hostname can no longer inject shell syntax.
